# ADR-0032：PDF 解析移入子进程

## 背景

知识库上传是管理端入口，但处理的是**不可信文件**。`docs/09` 的安全清单从 W6 起
一直挂着一条：「上传文件类型与大小限制；PDF 解析目前在 API 进程内，子进程隔离
尚未实现」。

现状并不是「完全没防护」：上传接口已经有扩展名/大小限制，解析放在
`asyncio.to_thread` 里，不会卡住事件循环。但线程只解决「阻塞」，不解决「崩溃」：

- `pypdf` / PyMuPDF 解析畸形 PDF 时可能段错误、死循环或吃光内存；
- 线程与 API 共享地址空间，解析库崩溃会直接带走进程；
- 一个 10MB 的压缩炸弹足以让单 worker 部署进入重启循环。

所以缺的是**故障隔离**，不是又一层超时参数。

## 备选方案

| 方案 | 结论 |
|---|---|
| 保持线程池 + 更严格的文件限制 | 否决。限制挡不住解析器自身 bug；崩溃仍在 API 进程内 |
| `signal.alarm` / 超时中断 | 否决。Windows 没有 SIGALRM；中断 Python C 扩展也不可靠 |
| 容器/seccomp 单独跑解析 | 否决。私有化部署多一个需要维护的容器与镜像 |
| 外部解析服务（如 Gotenberg） | 否决。为一个低频管理操作增加一个组件 |
| `spawn` 子进程 + 管道 + 超时 | **采纳**。平台一致、无新依赖、崩溃与超时都能收敛 |

## 决策

1. **所有 PDF 都走子进程**：`parse_bytes` 遇到 `.pdf` 调用
   `parse_pdf_isolated()`，用 `multiprocessing.get_context("spawn")` 启动。
   选择 `spawn` 而不是 `fork`：Windows 没有 fork；Linux 上 fork 会复制数据库连接、
   锁与事件循环状态，子进程里都不该出现。
2. **解析逻辑原样搬进子进程**：原来的 PyMuPDF 优先 / pypdf 兜底逻辑改名为
   `_parse_pdf_inprocess`，只在子进程里执行，解析质量与格式支持不变。
3. **60 秒预算**：`PDF_PARSE_TIMEOUT_S = 60.0`。超时后 `terminate()`，2 秒不退再
   `kill()`。超时与崩溃都转成 `ParseError`，上传接口仍返回 422，错误文案说明是
   「PDF 解析超时/进程异常退出」。
4. **错误只跨进程传文本**：`ParseError` 原样带回消息；其他异常带类型名与消息；
   子进程提前退出（EOF）映射为「PDF 解析进程异常退出」。父进程不重新抛子进程的
   异常对象，避免把内部 traceback 暴露给上传者。
5. **父进程必须收尾**：子进程 `daemon=True`；无论成功、失败还是超时，`finally`
   都会 `join(1s)`，仍存活则终止，避免僵尸进程。管道两端都显式关闭。
6. **不引入常驻 worker 池**：上传是低频管理操作，本机 Windows 实测 1 页文本 PDF
   预热后 5 次中位数约 0.30 秒启动开销（同文件进程内解析 0.0006 秒，仅作对照），
   可接受；常驻池需要处理复用、版本升级与泄漏，当前收益不足。也不做内存 `rlimit`
   （Windows 无对应实现），本轮只保证「崩溃不带走 API、超时能终止」。
7. **不改 API 契约**：仍由 `KnowledgeBase.index_bytes` 在线程池里调用
   `parse_bytes`，上传接口、422 文案与 `docs/03` 不变；扫描件仍因无文本层被拒。

## 后果

- 恶意/畸形 PDF 最多让一个子进程崩溃或被杀，API 继续服务并返回 422。
- 每次 PDF 上传多一次进程启动开销：本机 Windows、1 页文本 PDF、预热后 5 次中位数
  约 0.30 秒（同文件进程内解析 0.0006 秒；Linux 与大文件未测）；查询与检索不受影响。
- 子进程仍继承环境变量、工作目录与文件系统权限——这是**故障隔离**，不是安全沙箱；
  真要防提权需要容器/seccomp，属于部署层。
- 60 秒是常量而不是环境变量：慢机器上更大的 PDF 可能被误杀；真有需要再加配置与
  对应 ADR，而不是先加一个没人调的旋钮。
- 并发上传 PDF 会并发出多个子进程；管理端入口本身有鉴权与频率限制，本轮不加
  额外的解析并发闸门。

## 验证

- 新增 `server/tests/test_rag_pdf_isolation.py`：文本 PDF 经子进程解析成功；
  坏 PDF 的错误跨进程变成 `ParseError`；`timeout_s=0.01` 触发超时文案。
  既有 `test_rag_parse.py` 与上传 422 用例全部走新路径。
- 默认 `uv run pytest`：**425 passed + 31 skipped**；真实 Postgres：
  **453 passed + 3 skipped**；再加 Redis：**456 passed**。
- `ruff check` / `ruff format --check`（171 files）/ `mypy app`（104 files）通过。
- 启动开销：本机 Windows，1 页文本 PDF，预热后 5 次中位数 **0.303 秒**（同文件
  进程内 `_parse_pdf_inprocess` 中位数 0.0006 秒，仅作对照；大文件与 Linux 未测）。
- 前端未改，仍 63 tests / 13 files；检索、提示词、多轮判定未改，未重跑评测。

## 待定

- 子进程内存上限（POSIX `resource.setrlimit` / Windows Job Object）。
- 常驻解析 worker 池，省掉每次上传的进程启动开销。
- 解析超时是否开放环境变量（需先有真实大文件样本与性能口径）。
- 并发上传的解析闸门与排队。
- OCR：扫描件目前直接 422，属于产品能力而不是本 ADR 的隔离范围。
