# 0025 · 追问的原句优先：新话题不再被上一轮稀释

- 状态：已采纳（W6 后补）
- 日期：2026-11-10
- 相关：[docs/04-agent-design.md](../04-agent-design.md)、[docs/05-rag-design.md](../05-rag-design.md)、
  [docs/08-eval-metrics.md](../08-eval-metrics.md)、[ADR-0020](0020-multi-turn-context.md)、
  [ADR-0024](0024-multiturn-eval.md)

## 背景

[ADR-0024](0024-multiturn-eval.md) 的多轮评测发现并**留着没修**一个缺陷：

- 「公司笔记本整机保修几年」→「那报销怎么走」：合并检索词后，回答引用了保修文档，
  而语料里明明有《差旅报销流程》；
- 这不是孤例：「那会议室怎么订」「那蓝屏呢」「那VPN怎么连」都一样——追问里点名了
  新话题，却因为拼了上一轮的问题被旧话题压住；
- ADR-0024 的「待定」记了三种修法（双检索 RRF、原句优先、名词短语判定），
  共同顾虑是"会影响主集召回与延迟"，所以留到单独决策。

难点在**判定**，不在拼接：

1. **长度和指代词分不开**。「那报销怎么走」只有 6 个字，却是新话题；「那要多久」
   同样短，却是地道的追问。
2. **检索分数也分不开**。单独检索时「那怎么申请」的 0.710 比「那报销怎么走」的
   0.631 还高——分数衡量的是"像不像某篇文档"，不是"有没有点名某篇文档"。
3. **合并一定赢**。合并句里旧话题的词更多，旧文档分数更高（打印机 0.916 vs
   VPN 0.721），不改变检索词就不可能答到新话题。

## 备选方案

| 方案 | 否决理由 |
|---|---|
| 维持合并，把边界写进文档 | 缺陷是真的答错话题，不是"不够好"；README 已经挂了一条已知边界，再挂一条说不过去 |
| 原句检索只要分数够高就优先 | 「那要多久」单独检索 0.764、且只有一篇文档，会去答《软件安装流程》；「那怎么申请」也比报销高，阈值分不开 |
| 双检索 RRF（原句 + 合并句） | 合并句的第一名通常分更高，RRF 只能让两篇都进引用，回答会同时讲两个话题；判定会退化成"引用里有对的就算过"，给假通过开口子 |
| 名词短语 / 词性判定话题头 | 没有分词器与词性标注；「报销」本身既是名词也是动词，最后仍要靠词表 |
| 让模型改写查询（follow-up rewrite） | 方向正确，但 mock 模式量化不了收益；会改变「8 节点只有 2 个调 LLM」的基线，需要单独决策（列入待定） |
| **原句优先 + 话题头证据 + 分差** | 两个证据都能规则判定、可评测；漏判时退化为现有行为，不会比现在更差 |

## 决策

### 1. 原句优先（`app/agent/nodes/retrieve.py`）

追问（`context_query != query`）先按**原句**检索一次：

- 如果 `names_top_document(query, hits)` 成立，就用这次结果，`context_query` 记原句
  （`finalize` 选句也随之用原句，不会拿旧话题的词去挑句子）；
- 否则再按合并句检索（ADR-0020 的现有行为），`context_query` 记合并句；
- 原句检索抛异常按"点不出"处理，继续走合并查询——多一次检索不能让 run 更容易挂；
- 单轮问题不走这条分支（`context_query == query`），主集 50 条指标零变化。

代价是追问多一次检索（含一次向量化）。mock 内存索引下可以忽略；真实嵌入服务下
这条路径的延迟没有基准（见「待定」）。

### 2. 两个证据缺一不可（`names_top_document`）

**证据一：话题头出现在第一名文档的标题里。**
`history.topic_head()` 取**疑问词之前**那截文本（「那报销怎么走」→「那报销」，
「那怎么处理」→「那」），去掉单字 token 后要求与第一名文档标题共享一个 ≥2 字的词。

- 「那怎么处理」的话题头只剩一个「那」：「处理」是问法里的谓语，不是话题——
  否则会去答《账号密码重置与锁定处理》；
- 「那要多久」的话题头是「那要」：它同样不该去答《软件安装与权限申请流程》；
- 「那报销」的「报销」在《差旅报销流程》标题里，这才是"点名了一篇文档"。

疑问词表（怎么/什么/多久/呢…）是**问法**词表，不含任何业务词：业务词随语料变，
问法不会。

**证据二：第一名比第二名（不同文档）高出 ≥ 0.10。**
泛化追问也能检索到文档，但多篇分数咬在一起（《工位调整申请》0.710、《停车位申请
说明》0.704、《软件安装与权限申请流程》0.671），说明原句并没有点到哪一篇，这时
拼上文反而更可信。0.10 是实测的"明显领先"线：点名追问的分差是 0.21–0.32，
泛化追问只有 0.01–0.03（表见 [multiturn-v2](../eval/multiturn-v2.md)）。
同一篇文档的多个切片不参与第二名比较——它们本来就是同一个答案。

两条都成立才丢掉上文。**漏判的代价是退化成现有的合并行为**，不会比现在更差。

### 3. 评测：新增 `shift_acc`，与 `coref_acc` 分开记

「新话题不被劫持」和「指代上一轮」是相反的方向，混成一个指标会让两边都说不清：

- `kind: shift` 用例：追问轮必须命中新话题文档，**且不得引用上一轮话题的文档**；
  隔离对照方向反过来——空会话**必须**命中所列新文档，用来守住用例档位
  （如果单独提问都命不中，这句话其实是追问）；
- 4 条切换（报销 / 会议室 / 蓝屏 / VPN）+ 3 条指代**守卫**（「那怎么申请」
  「那流程是什么」「那怎么处理」：泛化追问必须继续用上文）+ 1 条诊断项；
- 门槛 `shift_acc ≥ 85%`，与 `coref_acc` 并列；
- loader 强制：shift 必须写 `must_not_cite_docs`、不能标 diagnostic；coref 不许写
  `must_not_cite_docs`；没有 shift 用例直接报错（否则 `shift_acc` 是空指标）。

守卫用例是这次新增里最重要的部分：它们**反向**证明"原句优先"没有过度触发。
只加切换用例的话，把判定放宽就能全过，指标失去意义。

### 4. 未覆盖的边界留在诊断项

「那公司年会抽奖怎么规定」这类**没点名任何文档**的新话题，话题头匹配不到标题，
仍会合并、仍会被上一轮带偏：诊断项 **0/1**，不计入两条指标。要修只能让模型改写
查询（见「待定」），不在本次动检索。

## 后果

- 「那 + 新话题」从"已知边界"变成"点名文档就能切"：README 的已知边界收窄为
  "没点名文档的新话题"。
- 多轮评测从 9 条正例扩到 **16 条**（12 指代 + 4 切换）+ 1 条诊断；`coref_acc`
  与新的 `shift_acc` 都有回归信号。
- 追问路径**多一次检索**：先原句、点不出再合并。mock 内存索引下可忽略；
  真实嵌入服务下未做延迟基准。
- 两个常量与语料相关：分差 `0.10`、疑问词表。语料明显变化或换检索器时要重跑
  `make eval-multiturn`；基线文档里留了各追问句的实测分差表。
- `topic_head()` 是纯文本切分，不碰检索、不碰存储；`names_top_document()` 在节点里，
  测试可以拿合成 hits 直接钉住两个条件。
- 评测判定仍是**文档级**、只判命中不判精度；答案选句质量仍归主集 `answer_acc`。

## 验证

- `tests/test_history.py` +2：话题头保留话题（那报销 / 那会议室 / 那蓝屏 / 那 VPN）、
  泛化追问的话题头是空的/只剩问法（那怎么处理 / 那怎么申请 / 那到底要怎么办）。
- `tests/test_rag_retrieve.py` +4：`names_top_document` 需要标题+分差两个证据、
  同文档切片不算第二名；节点在「那报销怎么走」时不拼上文（引用《差旅报销流程》）、
  在「那怎么申请」时仍拼上文；原句检索抛异常仍回落到合并查询。
- `tests/test_multiturn_eval.py` 18 → 27 条：新增 5 条 loader 约束（shift 缺
  `must_not_cite_docs`、coref 写了 `must_not_cite_docs`、shift 标诊断、未知 kind、
  没有 shift 用例）、2 条判定（引用上一轮话题、shift 前提）、2 条端到端
  （切换成功且不泄漏旧话题；把追问标成 shift 会被前提检查拦住）。
- 基线：[eval/multiturn-v2.md](../eval/multiturn-v2.md) —— `coref_acc 100%（12/12）`、
  隔离对照 12/12、`shift_acc 100%（4/4）`、切换前提 4/4、诊断 0/1。
- 主集回归：**50/50**、`cite_acc 97.09%`、`recall@5 100%`、`p95 79ms`（单次运行；单轮路径未改，
  与 [baseline-v1](../eval/baseline-v1.md) 的 81ms 属同一量级）。
- 完整回归：默认 **366 passed + 24 skipped**；带 Postgres **390 passed**；
  `ruff check` / `ruff format --check`（153 files）/ `mypy app`（96 files）通过；
  迁移无变化；前端未改动。

## 待定

- **没点名文档的新话题**（诊断 0/1）：要不要让模型把追问改写成独立问题
  （多一次调用、改变 2 个 LLM 节点的基线），还是做原句/合并句的双检索加权
- **分差阈值 0.10 的语料相关性**：语料翻倍、或换成 bge-reranker 后要重新标定
- **真实嵌入服务下追问多一次检索的延迟**：当前只有 mock 内存索引的数字
- 段落级指代与答案选句（当前只判文档级命中，选句归 `answer_acc`）
- 疑问词表是否需要覆盖更多问法（「那…的话」「那要是…」）；每加一个都要有用例兜底
