# ADR-0041：会话从列表移除（软移除）

- 状态：已采纳
- 日期：2026-11-12
- 关联：[ADR-0021](0021-data-retention.md)（保留清理）、[ADR-0030](0030-session-list.md)（会话列表）、[ADR-0033](0033-session-history-pagination.md)（分页）、[ADR-0040](0040-session-rename.md)（重命名）

## 1. 背景

ADR-0030 的会话列表是 `runs.session_id` 的投影，ADR-0040 又加了旁挂的显示标题。
但用户至今没有办法把不想要的会话从侧栏拿掉——重命名只能改显示名，不能减少列表项。
ADR-0040 的「待定」里记着删除，并明确要先回答一个问题：删的是**会话**，还是**数据**？

把 `runs`、`events`、`approvals` 真正删掉不可接受：

- 事件与审批是治理证据，R1 要求只增不改，ADR-0021 只允许按时间清理，不允许用户按行删；
- `runs` 是回放、成本、审计的来源，硬删会留下 `model_calls`、事件、审批的孤儿；
- 删除语义一旦开放，就要处理「删到一半失败」「删除后重放」「别人能删我的吗」等一串问题。

因此本轮只做**列表级移除**：用户看不见这个会话，但数据仍按保留期存在。

## 2. 备选方案

| 方案 | 结论 | 原因 |
|---|---|---|
| 物理删除 `runs` 及其事件/审批 | 否决 | 破坏只增不改与审计；级联删除的失败语义难讲清 |
| 只删 `session_titles` 行 | 否决 | 没有自定义标题的会话仍会出现，解决不了问题 |
| 前端 localStorage 隐藏 | 否决 | 换设备/换浏览器就回来；搜索结果仍会出现；与服务端分页冲突 |
| 新建 `sessions` 生命周期表并标 `deleted` | 否决 | 为「隐藏」引入会话主表，和现有投影模型冲突，收益不抵迁移成本 |
| 旁挂 `hidden_sessions`，列表/搜索过滤 | **采纳** | 不动 `runs`/事件/审批；天然按用户隔离；无迁移数据；以后要恢复只需删一行 |

## 3. 决策

1. **表**：`hidden_sessions`（`user_id VARCHAR(64)`、`session_id VARCHAR(64)`、`hidden_at TIMESTAMPTZ`），
   复合主键 `(user_id, session_id)`，无外键、无额外索引。主键即查询路径；表只存用户主动移除的会话，
   量级远小于 `runs`。迁移 `0017`。
2. **接口语义**：`RunStore.hide_session(user_id, session_id)` 先确认该用户确有这个会话的 run；
   没有返回 `False`（API 404，不泄露别人的会话）；重复移除返回 `True`（幂等）。
3. **列表与搜索过滤**：`list_sessions` 在聚合时排除 hidden 会话；标题搜索同样排除。
   除这两处外不改任何读路径——直接 `GET /runs/{id}`、事件回放、引用预览仍可访问，
   因为这是同一用户自己的数据，移除只是侧栏整理，不是权限控制。
4. **API**：`DELETE /api/sessions/{session_id}`。成功 204；别人的/不存在的会话 404；
   `SQLAlchemyError` → 503 `DATABASE_UNAVAILABLE`；重复调用仍 204。
5. **前端**：移除入口放在侧栏每行的垃圾桶按钮，二次确认用**行内**确认框，不为一次移除引入全局弹层；
   移除的是当前会话时切到新会话，再按当前搜索词刷新第一页；失败写 `sessionsError`，不改本地列表。
6. **不做硬删除、不发事件**：保留清理仍按 ADR-0021/0023 的时间口径；隐藏行为本身不进入事件流，
   与重命名一致（管理动作，不是 Agent 运行的一部分）。
7. **v1 无恢复入口**：隐藏后重新打开需要直接访问 run 详情或改库；恢复/撤销留到后续 ADR。
8. **没有管理员旁路**：会话列表本来就只读本人，管理员看不到别人的侧栏，也就不存在「代删」。

## 4. 后果

- 用户可以把侧栏收敛到真正关心的会话，搜索也不会被已移除的会话干扰。
- **数据没有消失**：正文、引用、运行过程、审批仍按保留期保存；「从列表移除」的文案必须写清这一点，
  避免被理解成删除数据。
- 已隐藏的会话在 `hidden_sessions` 里留一行；如果对应 `runs` 行后来被手动删除（保留清理只清事件/正文/计量，不删 run 行），这一行会变成孤儿。
  当前不清理（表小、无 join 副作用），列入待定。
- 没有「最近删除」/撤销；误点后只能重新找到 run id 或等后续版本。
- 队列/搜索的可见性只在列表层，跨用户不可见；同一用户换设备后一致（服务端存储）。

## 6. 待定

- **恢复入口**：✅ 已由 [ADR-0043](0043-hidden-session-restore.md) 兑现——侧栏「已移除的会话」
  折叠区 + `DELETE /sessions/{id}/hidden`；恢复只删 `hidden_sessions` 行，不重建 run/事件/审批。
- **按用户删数据**：真正的「数据主体删除」不是列表移除，需要 IdP 身份目录、跨表级联与审计，
  单独立项。
- **隐藏行清理**：`runs` 被保留清理后，`hidden_sessions` 的孤儿行是否随 run 删除一并清；
  当前选择不清理，等真实数据量再定。
- **管理员视角**：是否需要看某用户的会话列表（含已移除）；这会引入新的权限模型。
- **批量移除**：v1 一次一个；批量需要批量确认与部分失败语义。
