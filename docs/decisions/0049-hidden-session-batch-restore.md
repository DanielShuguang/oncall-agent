# ADR-0049：已移除会话的批量恢复

## 背景

ADR-0043 给「已移除的会话」加了单条恢复，ADR-0047 又给它补了游标分页与标题搜索。
但恢复仍然一次只能点一个：用户想清理十几个误移除的会话，就要发十几次 `DELETE`，
中途失败还会留下「恢复了一半」的界面状态；前端只能逐条等待、逐条刷新列表。

软移除本身不删 run，恢复也只是删 `hidden_sessions` 里的一行（ADR-0041），所以批量操作
没有数据一致性问题，缺的只是一个能一次接收多个 id 的入口。

## 备选方案

| 方案 | 否决理由 |
|---|---|
| 前端循环调单条 `DELETE` | N 次往返；部分失败后要重新对齐整个列表；折叠区与主列表各刷新一次，状态更难讲清 |
| 「恢复全部已移除」 | 选择粒度太粗，用户通常只想恢复其中几条；也无法表达部分成功 |
| 批量端点 + 逐条结果 | 需要为每个 id 返回 `restored`/`missing`/`forbidden`，响应与前端展示都变重；v1 只需要计数 |
| 批量端点 + 计数（采纳） | 一次往返；去重、限长后交给存储层一次删除；返回实际恢复数，前端重新拉一页即可对齐 |

## 决策

1. **新端点**：`POST /api/sessions/hidden/restore`，body `{"session_ids": ["sess_...", ...]}`；
   一次 1–50 个，服务端去重保序，超过 50 或空列表返回 422。
2. **只删本人的隐藏行**：按 `(user_id, session_id)` 删除；不存在的、别人的、本来就没移除的 id
   直接忽略（部分成功），不报错、不泄露别人的会话是否存在。
3. **返回计数**：`{"restored": n, "requested": m}`，`m` 是去重后的请求数。客户端不按 id
   对账，成功后重新拉当前页与主列表，避免「部分成功」时本地列表撒谎。
4. **幂等**：同一批再调一次返回 `restored: 0`；不写事件、不写审计、不改 run/审批/引用。
5. **存储层**：`RunStore.unhide_sessions(*, user_id, session_ids) -> int`；内存实现逐个
   `pop` 计数；Postgres 用 `DELETE ... WHERE user_id = :u AND session_id IN (...) RETURNING
   session_id` 一次删除并计数。API 负责去重与 50 上限，存储层不做二次校验。
6. **前端**：折叠区每条加复选框，另有「全选当前页」；「恢复选中（N）」在请求中禁用。
   恢复成功后清空选中、递增 `hiddenRequest` 令牌、重新拉一页已移除列表并刷新主列表；
   搜索、关闭折叠区、单条恢复、隐藏会话都会清空选中，避免对已消失的 id 再发请求。
7. **范围**：无迁移、无新索引、无管理员旁路；v1 不返回每条结果，也不做「恢复后直接打开」。

## 后果

- 批量恢复从 N 次请求降为 1 次；部分成功时界面以服务端重新拉取的结果为准，不再需要
  「哪些成功了」的本地推断。
- 代价是响应只有计数：如果以后要告诉用户「这 3 个不属于你」，需要升级为逐条结果或
  在请求前去重过滤。当前选择是静默忽略，符合不泄露存在性的原则。
- 恢复仍只删 `hidden_sessions` 行：不重建 run，也不改变正文/事件的保留期（ADR-0021/0023）。

- 后端默认 **479 passed + 36 skipped**；真实 Postgres **512 passed + 3 skipped**；
  Postgres + Redis **515 passed**。

- 前端 `tsc --noEmit`、**73 tests / 15 files**、`oxlint` 0/0（66 files）、
  `oxfmt --check`（74 files）、`pnpm build` 252ms。
- 契约用例覆盖：本人两行批量恢复、重复 id 去重、不存在/别人的 id 忽略、空列表/51 个/空
  id 422、重复恢复 0、内存与 Postgres 一致。

## 待定

- 逐条结果（`restored` / `missing` / `forbidden`）与前端提示；
- 恢复操作的审计（谁在何时恢复了哪些会话）；
- 管理员跨用户恢复与批量清理隐藏行；
- 「恢复并打开」的一次点击路径。
