# ADR-0079：刷新恢复上次会话

## 背景

会话列表（ADR-0030）已经能回看最近会话，但刷新页面后前端总是落回「新会话」空态。
用户正在排查的问题、刚看过的引用和审批，都要重新从左侧列表点一次；对演示和日常使用都很打断。

这个仓库没有前端路由：`App.tsx` 只有「对话 / 运行 / 管理后台」三个顶层 tab，
会话 id 不进入 URL。因此「刷新后回到上次会话」本质上是**浏览器本地偏好**，不是服务端事实。

## 备选方案

| 方案 | 否决原因 |
|---|---|
| 把会话 id 放进 URL（`/?session=...`） | 需要引入路由状态、处理前进/后退与分享；本项目的页面切换是简单 tab，没有路由层 |
| 服务端保存「用户最后打开的会话」 | 需要新表/迁移与写接口；只是客户端体验，不值得增加服务端状态 |
| `sessionStorage` | 关闭标签页即丢，刷新可用但「下次打开」仍回到新会话，价值不完整 |
| 无条件打开存储的 id | id 可能已被移除、已删除、不属于当前用户；直接 `getSessionRuns` 会 404 或越权 |
| 不恢复（现状） | README 已列为已知局限；每次刷新都丢上下文 |

## 决策

1. **只存 session_id**：`localStorage` 键 `oncall.last-session.v1`；
   读取时 `trim()`、长度 1–64，空/超长/存储异常都按「没有记忆」处理。
   不存 transcript、标题或轮数，减少本地隐私面。
2. **会话 id 变化时写入**：`ChatPage` 在 `sessionId` 非空时写入；
   「新会话」以及「隐藏当前会话/批量移除当前会话」会先清空记忆，避免下次刷新回到一个不该再出现的会话。
3. **首屏列表返回后再决定是否恢复**：`GET /sessions` 第一页（20 条）返回后，
   只有同时满足以下条件才自动打开上次会话：
   - 本次页面尚未恢复过（只尝试一次）；
   - 用户还没有进入任何会话；
   - 用户没有正在发送消息；
   - 用户没有手动点过会话；
   - 存储的 id 在当前用户第一页列表里。
   不在第一页、已隐藏、已删除、属于别人都不会恢复，而是保持新会话。
4. **恢复过程复用现有历史加载**：按 `getSessionRuns(last, 20)` 拉首屏历史，
   失败只提示「上次会话加载失败」，不清除记忆、不阻塞新会话。
5. **竞态防护**：首屏列表响应可能晚于用户的点击或发送。`onSelectSession`、`onNewSession`
   和 `onSend` 都在入口同步设置 `sessionSelectionStarted`，列表 `.then` 看到它就不再自动恢复；
   另一个 `sessionIdRef`/`sendingRef` 防止用户已经开始对话后又被恢复覆盖。
   发送入口单独设 guard 是因为 `send()` 会创建/占用当前会话，自动恢复若晚一步会 `switchSession`
   并 abort 掉刚发出的运行。自动恢复占用 `historyLoading` 时仍允许改选其他会话：
   用户的点击优先，旧恢复响应按 `historyRequest` token 丢弃。
6. **不引入后端/迁移**：会话本身仍由服务端列表和 `runs` 查询保证归属与可见性；
   本地只记录「上次打开的是哪个 id」。

## 后果

- 刷新后，如果上次会话仍在第一页，会直接回到该会话；否则落回新会话。
- 只覆盖首屏 20 条：更早的会话即使记得也不会自动打开，用户仍需从列表点开。
- 按浏览器保存，不跨设备；共享同一浏览器 profile 的另一个账号不会打开别人的会话
  （id 不在其第一页，且历史查询带 token），但会继承上一个账号的「上次会话 id」，
  下次该账号自己的列表若恰好包含同一 id 才会恢复。由于 id 是 UUID、会话归属服务端校验，
  不存在跨用户读取。
- 清除浏览器站点数据后回到新会话；存储不可用（隐私模式等）时静默降级。
- 隐藏/删除/回收后的会话不会恢复，记忆可能短暂保留旧 id，直到下一次打开新会话覆盖。

## 待定

- 是否把「上次会话」写进 URL，以支持分享/深链；
- 是否允许恢复第一页之外的会话（先按 id 探测详情，或改成分页查找）；
- 是否尊重「多标签页」：两个标签各自打开不同会话时，最后写入者获胜；
- 是否增加「不要在刷新时恢复」的用户开关。
