# ADR-0073：会话置顶数量上限

- 状态：已采纳（W6 后补）
- 日期：2026-11-15
- 相关：[ADR-0069](0069-session-pin.md)、[ADR-0030](0030-session-list.md)、[ADR-0072](0072-session-batch-hide.md)

## 背景

ADR-0069 把置顶做成了每个用户的列表偏好：`pinned_sessions` 以
`(user_id, session_id)` 为主键，列表先按置顶分组、组内再按最近活动排序。

当前置顶没有数量上限。置顶是「列表偏好」而不是会话数据，单个用户可以无限
增长置顶行；置顶组会持续压在第一页上方，把真正最近的会话挤出首屏，也让
`GET /sessions` 的置顶段扫描无界。ADR-0069 的「待定」里专门记了
「置顶数量上限与『置顶太多』的提示」。

## 备选方案

| 方案 | 结论 | 原因 |
|---|---|---|
| 不设上限，只在前端提示「置顶太多」 | 否决 | 提示不阻止数据增长，列表仍会被压垮 |
| 数据库唯一约束/触发器限制 | 否决 | 需要迁移与数据库特定逻辑，跨库（内存/PG）行为不一致 |
| 达到上限时自动淘汰最久未活动的置顶 | 否决 | 静默改变用户偏好，用户无法预期 |
| 每次请求最多置顶 N 个（批式上限） | 否决 | 约束的是单次请求，不是用户总量 |
| 配置化上限（环境变量） | 暂缓 | 当前没有按部署调参的需求；固定值更容易解释与测试 |
| **固定软上限 50，置顶时检查** | **采纳** | 约束总量、实现小、内存/PG 同口径，不新增迁移 |

## 决策

1. **上限为 50**：`server/app/core/store.py` 定义
   `MAX_PINNED_SESSIONS = 50`。上限按用户（`user_id`）统计，不同用户互不影响。
2. **幂等优先**：`pin_session` 先判断「该会话是否已经置顶」。已置顶时直接返回
   `True`，不因当前已满而失败；只有**新增**置顶才检查数量。
3. **超限抛领域异常**：新增 `PinLimitExceeded`，由 API 层翻成
   `409 {"code":"PIN_LIMIT_REACHED"}`，消息带上限。未置顶时仍先做可见性检查，
   不存在/别人的/已隐藏会话继续返回 404，不因为「满了」而泄露存在性。
4. **内存与 PG 同口径**：内存实现按 `_pinned_sessions` 计数；PG 在
   `pin_session` 事务内先查是否已存在，再 `count(*)`，超过上限抛异常。两者都
   不改 `updated_at`、不写审计。
5. **软上限**：检查与插入不在同一行锁上完成；并发置顶可能短暂超过 1 个。这个
   偏差可接受，下一次置顶会继续被拒；不做 advisory lock / 串行化。
6. **既有数据不回溯**：已经超过 50 个置顶的用户不会被自动清理；仍可取消置顶，
   只有新增置顶会被拒。恢复已移除会话时也不会恢复原置顶（沿用 ADR-0069）。
7. **前端不新增交互**：继续沿用 ADR-0069 的置顶按钮；409 由现有 `sessionsError`
   展示，用户取消其他置顶后可重试。旧后端没有该上限时前端行为不变。

## 后果

- 置顶总量有界；首屏置顶段最多 50 行，列表性能与可预期性更好。
- 上限是**用户维度**的资源约束，不改变会话内容、权限或可见性。
- 并发下可能短暂出现 51 个置顶；文档明确写成软上限，不承诺强一致。
- 上限固定为 50，不提供环境变量；如果后续需要按部署调整，再单开 ADR。
- 没有「置顶计数」接口；前端在 409 时才知道已满。

## 验证

- `server/tests/test_sessions_api.py::test_pin_session_limit`：上限设为 1 时，
  第一个置顶 204、重复置顶 204、第二个 409 `PIN_LIMIT_REACHED`；取消后可再置顶。
- `server/tests/test_store_contract.py::_exercise_pinned_sessions`：在内存与 PG
  契约中把上限临时设为 1，已置顶幂等，新增超出抛 `PinLimitExceeded`。
- 默认 **506 passed + 40 skipped**；真实 Postgres **543 passed + 3 skipped**；
  Postgres + Redis **546 passed**；`ruff check`、`ruff format --check`（196 files）、
  `mypy app`（114 files）通过。
- 前端 **94 tests / 19 files**、tsc、oxlint 0/0（75 files / 231 rules）、
  oxfmt 83 files、`pnpm build` 通过；本 ADR 未改前端代码，计数与 ADR-0072 相同。

## 待定

- 上限是否改为环境变量/租户策略。
- 达到上限时是否在置顶按钮上提前禁用（需要列表返回计数或用户信息）。
- 置顶操作审计（谁在何时置顶/取消置顶）。
- 置顶组的拖拽排序/自定义顺序。
