# ADR-0067：会话恢复审计按日期范围

- 状态：已采纳
- 日期：2026-11-14
- 相关：[ADR-0059](0059-session-restore-audit.md)、[ADR-0060](0060-session-restore-audit-pagination.md)、
  [ADR-0062](0062-session-restore-audit-export.md)、[ADR-0064](0064-session-restore-audit-total.md)、
  [ADR-0065](0065-session-restore-audit-stats.md)、
  [ADR-0066](0066-session-restore-audit-stats-filters.md)

## 背景

会话恢复审计的列表、首屏总数、CSV 导出与统计已经支持 `user_id`/`session_id`
过滤；列表和导出按 `(restored_at, id)` 倒序翻页，统计支持「最近 N 天」窗口。
但管理员做交接、事故复盘或月度对账时，通常只有一段具体日期，例如「10 月 1 日到
10 月 7 日」，现有能力只能：

1. 按「最近 30 天」近似，窗口边界对不上；
2. 全量拉取后在客户端按 `restored_at` 过滤，游标、首屏 `total`、导出与统计
   会各算各的，口径不一致。

审计独立保留 365 天，按自然日范围查询是这一段数据的自然访问方式。

## 备选方案

| 方案 | 结论 | 原因 |
|---|---|---|
| 只给列表加日期范围 | 否决 | 导出/统计仍会与列表口径不一致 |
| 用 `days` 表示任意区间 | 否决 | 无法表达「某段历史日期」，且容易与统计的滚动窗口混淆 |
| 支持单端开放区间 | 否决 | 运维查询以完整日期段为主；单端会让「最近 N 天」和「某日之后」两套语义并存 |
| offset 分页配合日期范围 | 否决 | 列表已有 keyset 游标（ADR-0060），换一套分页会破坏既有契约 |
| 日期范围只作用于列表，导出/统计继续全量 | 否决 | 导出与统计正是交接/对账最常用的入口 |
| UTC 自然日闭区间，列表/导出/统计共用 | 采纳 | 与现有 `restored_at` 时间语义、`daily` 的 UTC 日一致，口径统一 |

## 决策

1. **统一参数**：`GET /admin/session-restores`、`/export`、`/stats` 都接受
   `restored_from`/`restored_to`（`YYYY-MM-DD`）。两端必须同时提供；`from <= to`；
   跨度最多 365 天（与审计保留期一致）。缺失一端、倒置或超长返回
   `422 {"code":"INVALID_RANGE"}`。
2. **窗口换算**：`since = from 00:00:00Z`，`until = to 23:59:59.999999Z`，闭区间；
   与列表的 `restored_at` 比较，与统计 `daily` 的 UTC 自然日一致。不做服务端时区
   换算，页面明确标注 UTC。
3. **统计与 `days` 二选一**：`days` 改为可选（不传默认 30）；带日期范围时不能
   同时传 `days`，否则 422。返回的 `days` 对自定义范围为
   `(to - from).days + 1`，客户端不需要自己算窗口长度。
4. **游标绑定日期范围**：列表游标在原有 `{t,i,u}` 上按需增加 `s`（session 过滤）
   与 `d`（`from:to`）。解码时按当前请求动态构造期望键集合，`d` 不一致返回
   400 `INVALID_CURSOR`；不带日期范围的请求仍保持旧游标形状，滚动升级期间旧
   实例继续可用。
5. **无迁移、无新索引**：`restored_at` 已有
   `idx_session_restore_audits_time`；列表/计数/导出/统计复用同一索引。日期范围
   只是在该索引上追加范围条件，不新增表或列。
6. **前端跟随已应用过滤**：审计页新增起止日期输入；应用时校验两端与顺序，
   清除时一并清空。统计卡与列表、导出使用同一组已应用的过滤；有日期范围时隐藏
   「近 7/30/90 天」快捷按钮并显示自定义范围，避免出现「按钮选 7 天、实际按日期
   范围统计」的错觉。应用/清除过滤或切换统计窗口时立即清空旧列表/旧统计并
   递增请求 token，避免新条件下闪现旧数据或旧响应回写。
7. **范围**：不做单端开放区间、按小时/按天下钻、统计缓存、页码/跳页；日期范围
   本身已可通过游标翻页。列表/计数/统计仍是独立查询，不是同一快照。

## 后果

- **口径统一**：列表、首屏 `total`、导出和统计使用同一组 `user_id`/`session_id`/
  日期条件，交接与对账不再需要客户端二次过滤。
- **索引选择性**：365 天窗口可能覆盖大部分审计行，范围条件的选择性有限；当前
  数据量下可接受，暂不引入额外索引或物化表。
- **滚动升级**：不带日期范围的游标保持 `{t,i,u}`（或 `{t,i,u,s}`），旧实例仍能
  解码；带日期范围的新游标只在本次请求内使用，旧实例拒绝是预期行为。
- **前后端版本**：本 ADR 之前的后端不认识 `restored_from`/`restored_to`，FastAPI
  会忽略未知 query 参数并返回未按日期过滤的结果；前端无法从 JSON 响应识别。
  因此部署时要求前后端同版本发布，本 ADR 不做能力协商或响应版本字段。
- **两次查询**：首屏仍会多一次 COUNT；统计与列表也不是同一快照。窗口内新增
  记录可能不出现在已翻过的页，和 ADR-0060/0064 的既有边界一致。
- **UTC 固定**：日期按 UTC 自然日解释，不随浏览器时区变化；页面已标注，避免
  本地时区跨日造成误解。

## 验证

- 默认：**500 passed + 40 skipped**（19.91s）
- 真实 Postgres：**537 passed + 3 skipped**（94.09s）
- Postgres + Redis：**540 passed**（93.98s）
- `ruff check` 通过；`ruff format --check` **194 files**；`mypy app` **113 source files**
- 前端：**85 tests / 17 files**、`tsc --noEmit`、`oxlint` 0/0（72 files）、
  `oxfmt --check` 80 files、`pnpm build` 通过
- 覆盖：列表日期过滤/首屏 total/翻页/换范围游标 400/旧范围与空结果、日期范围
  与 `user_id`/`session_id` 组合过滤及组合游标；导出 `X-Export-Count`、统计
  `days=1` 与 `daily`、单端/倒置/超 365 天 422、统计同时带 `days` 与范围 422；
  内存与 Postgres store 契约均覆盖范围 list/count。

## 待定

1. 日期范围 + `user_id`/`session_id` 的组合索引或部分索引，需在真实审计量级上
   做查询计划验证，当前不做。
2. 按天/按小时下钻与日期范围的统计图，当前只提供稀疏 `daily`。
3. 可配置时区展示（当前固定 UTC），依赖部署环境的 tzdata/时区策略。
4. 日期范围的前端快捷预设（本周/上周/本月），当前由日期输入自行选择。
