# 导出审计日期快捷预设（ADR-0107）

## 背景

恢复审计页与置顶审计页都提供五个 UTC 日期预设（近 7/30/90 天、本月、上月），
导出审计页仍要求手填起止日期。管理员核对一次导出行为时通常只看最近几天，
手输日期既慢又容易把起止写反。

## 备选方案

| 方案 | 取舍 |
|---|---|
| 只在页面内联五个按钮，不抽组件 | 页面已接近 300 行上限，再加筛选逻辑会超限 |
| 预设只填草稿，仍需点「筛选」 | 多一步操作，且与审计页/置顶审计页的点击即应用不一致 |
| 记住上次预设 | 导出审计页没有本地偏好，新增 key 会增加跨页状态；先不做 |
| 复用 `auditDatePresets` + 抽取筛选卡 | 采用。算法/时区/高亮规则与另外两页一致 |

## 决策

1. 复用 `AUDIT_DATE_PRESETS`、`auditDatePresetRange`、`activeAuditDatePreset`；
   预设全部是 UTC 自然日闭区间，与导出审计 API 的 `[from 00:00Z, to+1d 00:00Z)` 对齐。
2. 点击预设立即应用：把预设日期合并进当前草稿，再走与「筛选」相同的
   `commitFilters(next)`；用户/资源草稿也一并生效，避免出现「日期已变但用户还是旧值」。
3. 高亮只由已应用过滤反推（`activeAuditDatePreset(filters.createdFrom, filters.createdTo)`），
   手填日期但尚未点筛选时不会提前高亮。
4. 日期仍要求两端同时提供；单端由 `commitFilters` 拦截，不发请求。
5. 不持久化预设；刷新页面回到空筛选。理由：导出审计页本来就不记忆过滤，
   单独记忆日期会让「当前筛选」与「上次预设」混淆。
6. 把筛选卡抽到 `ExportAuditFilterBar`，草稿类型/转换放到 `exportAuditDraft`，
   页面回到 300 行以内；不新增后端接口、表或迁移。

## 后果

- 管理员核对最近导出行为从「手填两个日期 + 点筛选」变成一次点击。
- 预设只覆盖整日，不能表达「今天 14:00 之后」；跨时区仍按 UTC。
- 页面首次加载仍为空筛选；预设不是持久偏好。
- 抽取筛选卡后，导出按钮/错误/提示仍与列表共用同一份草稿和过滤状态。
