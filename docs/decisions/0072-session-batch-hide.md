# ADR-0072：会话批量移除

- 状态：已采纳
- 日期：2026-11-15
- 相关：#ADR-0041、#ADR-0043、#ADR-0049、#ADR-0069

## 背景

会话可以从列表逐条移除（ADR-0041），但清理几个不再需要的会话必须重复点
「移除」并逐条确认。已移除列表已经有批量恢复（ADR-0049/0055），移除侧没有
对称能力；用户在网络排障后会同时留下多个一次性会话，逐条操作成本高。

## 备选方案

| 方案 | 取舍 |
|---|---|
| 前端循环调用单条 `DELETE /sessions/{id}` | 一个 id 404 就让后续循环中断，或者要吞掉错误；N 次请求、N 个事务，部分失败没有统一结果 |
| 只做前端多选、不新增后端 | 同上，且无法保证 50 个上限与「只删本人的行」在同一处校验 |
| 后端批量接口，返回计数 | 计数无法解释哪些 id 没移除；与批量恢复（ADR-0055）的逐条结果不一致 |
| 后端批量接口，返回逐条结果 | 一次事务、一个上限、部分成功语义清楚；前端只负责选择 ✅ |

## 决策

1. **接口**：`POST /sessions/hide`，body `{"session_ids": [...]}`；1–50 个，
   去重后处理；空列表、超过 50 个、空字符串 id 都是 422。
2. **部分成功**：只处理当前用户名下的会话；不存在、属于别人的 id 不写行、
   返回 `hidden: false`，不区分两种情况，避免泄露存在性。
3. **幂等**：已经处于已移除状态的 id 仍返回 `hidden: true`，不改变第一次的
   `hidden_at`；重复调用不会报错，也不会把别的用户的会话「偷」过来。
4. **返回**：保留 `hidden`（真正处于已移除状态的数量）与 `requested`（去重后
   请求数），并返回与去重后请求顺序一致的 `items: [{session_id, hidden}]`，
   与批量恢复的逐条结果对称。
5. **存储**：`RunStore.hide_sessions` 返回该用户名下确实存在、且现在处于已移除
   状态的 session_id 集合。内存实现先在锁内筛出本人会话，再 `setdefault`
   写入并清置顶；Postgres 用 `INSERT ... ON CONFLICT DO NOTHING` 加
   `DELETE pinned_sessions`，同一事务提交。
6. **置顶联动**：隐藏会话时同事务删除该用户的置顶行（ADR-0069）；恢复后不会
   自动回到顶部。
7. **前端**：会话列表增加「管理」模式，只对**当前已加载页**多选；全选也只覆盖
   已加载页。点击「移除选中」先显示行内确认，确认后一次请求；成功后刷新会话
   列表与已移除折叠区，成功提示按 `items` 区分部分失败。搜索或刷新替换当前页
   时，只保留仍在列表中的勾选，避免对不可见行执行移除。旧后端没有该端点时
   按钮返回 404，前端显示错误，不影响单条移除。
8. **不做**：不新增迁移/索引/审计表；不按标题或过滤条件批量移除；不提供撤销
   （仍有已移除列表可恢复）；不跨页累积选择。

## 后果

- 一次请求完成多选移除，部分失败有统一结果；没有新增表或索引。
- 「已移除」的 id 再次提交仍返回成功，这是幂等口径；调用方不能用
  `hidden: false` 区分「不存在」与「属于别人」。
- 选择只覆盖当前已加载页，翻页后之前的勾选会丢失；这是有意的，避免误删未
  展示的会话。
- 隐藏操作仍然没有审计（ADR-0059 只审计恢复）；管理员无法回答「谁在何时批量
  移除了哪些会话」。

## 待定

- 移除审计（需要新表 + 4 个入口写入）。
- 跨页选择或「按搜索条件移除」：误操作面更大，暂不做。
- 批量上限是否可配置；当前与批量恢复一致固定 50。
