# ADR-0048：审批积压与等待统计

- 状态：已采纳（W6 后补）
- 日期：2026-11-13
- 相关：ADR-0046（运行过程里的单条审批等待）、ADR-0043（审批列表）、ADR-0016（决议事务）

## 1. 背景

ADR-0046 把「某一个审批等了多久」放进了运行过程回放，但审批人打开审批中心时仍看不到
全局情况：现在压着多少单、最久的一单等了多久、最近一周平均/最长等待是多少。ADR-0046
的「待定」里也记着「跨 run 的审批等待统计（审批人视角/流程瓶颈）」还没做。

现有接口只能绕：

- `GET /api/approvals?status=pending` 有 `limit`（1–200）但没有总数；超过 200 条时
  前端只能看到一页，算不出真实积压。
- 已决议列表同样分页，且没有 `resolved_at` 过滤；要算「近 7 天平均等待」只能把整个
  列表拉下来在前端聚合，既慢又不准。
- 审批表数据量小，但把统计逻辑放在前端会让「审批人看到的数字」依赖页面是否加载完。

## 2. 备选方案

| 方案 | 否决原因 |
|---|---|
| 前端拉全量列表自己聚合 | 受 `limit` 限制；每次翻页/筛选都要重算；空列表与加载失败分不清 |
| 在 `GET /approvals` 响应里附带统计 | 列表接口给普通员工也开放，会把审批人视角的数字带给他们；每次列表请求都多算聚合 |
| 定时任务预计算到新表 | 统计是即时问题，新增表/迁移/调度不划算；数据量小，实时聚合毫秒级 |
| 复用 `expires_at` 估算等待 | TTL 是配置值，不是真实人工等待；会把「还没处理」算成「处理了」 |
| 新增独立统计接口（采纳） | 按需聚合；沿用列表的过期收敛（会写 expired 状态）；权限与列表一致；不改变现有接口契约 |

## 3. 决策

1. **接口**：`GET /api/approvals/stats?days=7`，`days` 1–90，默认 7；仅审批人角色，
   普通员工 403 `FORBIDDEN`；数据库故障 503，不返回 0 冒充「没有积压」。
2. **指标**：
   - `pending_count`：当前**未过期**的待办数量（`status='pending'` 且 `expires_at > now`）；
   - `oldest_pending_age_s`：最老未过期待办从 `created_at` 到请求时刻的秒数，无待办为 `null`；
   - `decided_count`：窗口内 `approved` + `rejected` 的数量；
   - `avg_wait_ms` / `max_wait_ms`：窗口内每单 `resolved_at - created_at` 的平均/最大值，
     无决议为 `null`。
   过期（`expired`）不计入人工等待，也不计入 `decided_count`——TTL 是系统行为，混进
   流程指标会虚高。
3. **先收敛过期**：统计前复用 `expire_due()`（单轮最多 200 条），并在聚合条件里
   同时要求 `expires_at > now`——即使积压超过单轮上限、还有已过期单没落状态，也不把
   它们算成「卡住」。时刻取在收敛之后，年龄与窗口边界以返回时的状态为准。
4. **存储层聚合**：`ApprovalStore.stats(since, now)`，内存实现一次遍历；Postgres 两条
   聚合查询（待办 `count/min(created_at)`，窗口内决议 `count/avg/max`），不在应用层
   拉全表。现有 `idx_approvals_pending(status, expires_at)` 覆盖待办计数；已决议窗口
   没有 `resolved_at` 索引，但审批表小、页面按需请求，暂不加索引（迁移成本大于收益）。
5. **服务层鉴权**：`ApprovalService.stats(identity, days)` 先 `_is_approver`，再算
   `since = now - days`；角色集合来自 `ONCALL_APPROVER_ROLES`，与决议使用同一判定。
6. **等待口径**：`resolved_at - created_at`，负数按 0 处理（时钟回拨/脏数据不产生
   负等待）；不按 `expires_at`、不按 run 开始/结束时间计算。
7. **隐私**：统计不返回逐条 `resolved_by`；按审批人分组只返回聚合的 `user_id` key，仍只给审批人看。
8. **前端**：审批中心顶部四张卡（待审批/最久已等、近 7 天已决议、平均等待、最长等待），
   决议成功后刷新；时长展示复用 `formatDurationMs`（从运行过程格式化抽到 `lib/format`），
   保证「1h 2m」「2d 3h」口径一致。v1 固定 7 天，不做时间选择器。

不做：按状态/风险等级继续下钻、积压告警、导出、历史快照、跨租户统计；按审批人/工具分组已由 ADR-0051 兑现。

## 4. 后果

- 审批人每次打开审批中心多 2 条聚合查询；审批表小，实测毫秒级。
- 统计是请求时快照，不缓存；多人同时打开会重复计算，数据量小可接受。
- `oldest_pending_age_s` 只反映请求时刻，不推送；页面停留久了数字会旧，刷新即更新。
- 已决议窗口没有 `resolved_at` 索引；审批量大到十万级再评估。
- 过期单在统计前被 `expire_due()` 收敛，可能顺带写 `approval.resolved`/`run.failed`
  事件，这是既有语义，不是新增副作用。
