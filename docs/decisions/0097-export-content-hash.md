# ADR-0097：导出 CSV 内容哈希留痕

- 状态：已采纳
- 日期：2026-11-19
- 相关：[ADR-0094](0094-export-download-audit.md)、[ADR-0095](0095-export-audit-retention.md)、
  [ADR-0096](0096-export-audit-list-export.md)

## 背景

ADR-0094 起，CSV 导出会记录「谁、什么资源、什么过滤条件、多少行、是否截断」。
但审计记录没有绑定文件内容：下载文件在传输或本地保存后被修改，管理员无法仅凭
审计行判断手里的 CSV 是否仍是服务端当时生成的那一份。ADR-0096 的待定项里也
列了「审计 CSV 的签名/哈希归档」。

真正需要的是可复核的内容完整性，而不是新的权限或异步导出。哈希可以离线复核，
不保存文件正文，也不需要引入密钥管理。

## 备选方案

| 方案 | 结论 |
|---|---|
| 不记录内容指纹，只记录行数/过滤条件 | 无法证明下载文件未被改动；不采纳 |
| 服务端保存整份 CSV 供事后比对 | 重复存储敏感数据，审计表会随导出无限膨胀；不采纳 |
| HMAC/数字签名 | 需要密钥分发、轮换与验签流程，当前管理员场景用不上；留作待定 |
| 对返回内容计算 SHA-256，随审计行保存 | **采纳**，实现最小、可离线复核 |

## 决策

1. **字段**：`export_audits.content_sha256`，`VARCHAR(64)`、可空；迁移 `0025`
   只加这一列，不改索引。旧记录保持 `NULL`，不做历史回填（原文件已不可得）。
2. **计算范围**：服务端实际返回的 CSV 字符串按 UTF-8 编码后计算 SHA-256，包含
   BOM 与 CRLF，因此与浏览器下载到的字节一致。
3. **写入时机**：`record_export` 增加可选 `content`；六个业务导出与导出审计自身
   导出都在 CSV 生成成功后传入内容，`content_sha256` 与 `row_count` 同一条审计
   写入。审计写入失败仍 503，不返回文件。
4. **读取**：管理员列表返回 `content_sha256`；列表 CSV 增加
   `content_sha256` 列，旧记录为空字符串；管理页在行数下显示前 12 位并用
   `title` 给出完整值。
5. **不做**：不保存 CSV 正文、不做 HMAC/签名、不做服务端验签、不在响应头额外
   返回哈希（避免多个副本/代理改写响应头造成新的「真相源」）。
6. **已知边界**：哈希只能证明「与记录当时的内容一致」，不能防止能直接改数据库
   的人同时改哈希；也不会覆盖已有旧记录。

## 后果

- 新导出的审计行多一列 64 位十六进制哈希；旧行显示空，不伪装成已校验。
- 导出审计自身导出时，哈希覆盖「本次返回的 CSV」；该 CSV 内还包含此前各行的
  哈希，形成可逐层核对的快照。
- 迁移 `0025` 可逆；降级丢弃哈希列，原审计行仍在。
- 管理员需要在本地用 `sha256sum`/浏览器工具计算下载文件哈希后与审计行比对；
  页面只展示短值，避免表格被 64 字符撑开。

## 验证

- 后端：`test_export_audits.py` 断言自身导出返回的 CSV 含
  `content_sha256` 列、审计行哈希等于 `sha256(res.content)`；内存/PG 契约
  覆盖字段写入与读取。
- 迁移 `0025`：空库 `upgrade → downgrade 0024 → upgrade` 通过。
- 既有 7 个导出端点仍通过；默认/PG/PG+Redis 计数与 ADR-0096 一致
  （527+40 / 564+3 / 567）。
- 前端：`ExportAudit` 增加可选 `content_sha256`；页面展示短哈希，
  `tsc`/`oxlint`/`oxfmt`/`build` 通过。

## 待定

- HMAC/签名与密钥管理；
- 下载完成后由客户端上报校验结果；
- 旧记录哈希回填（当前文件已不可得，不计划做）；
- 是否在响应头返回哈希（当前刻意不做，见决策 5）。
