# 0026 · 按用户的日预算：默认值 + 表覆盖 + 独立账本

- 状态：已采纳
- 日期：2026-11-11

## 背景

[ADR-0013](0013-model-gateway.md) 定了三层预算：单 run `ONCALL_RUN_BUDGET_CENTS`、
当日全局 `ONCALL_DAILY_BUDGET_CNY`，以及「预扣 → 结算」的 Redis 账本。缺的是**按人**：
全局预算花完，所有人一起停；反过来，一个大用户把当天额度烧光，运维只能调大全局值
或临时停服务。ADR-0013 的「待定」写的就是这件事——「是否把按租户/按用户日预算做成表」。

企业现场的问题是具体的：一个部门几百人共用一个部署，成本要能落到人头，改额度不该重启。

## 备选方案

| 方案 | 否决理由 |
|---|---|
| 维持全局预算，出事再人工处理 | 没有按人边界；大用户喝完，其他人被连坐 |
| 加一个「所有用户统一」的环境变量上限 | 粗粒度可用，但改上限要重启，也无法给某个人开白名单 |
| 每人一行日汇总表（Postgres） | 每次模型调用写库、并发要行锁；预算本来就允许"偏保守"，不值得为强一致付这个代价 |
| 两个独立 Lua 账本（全局一个、个人一个） | 预扣不是原子的：个人被拒时要回滚全局，进程崩在两次调用之间会漏；与全局账本重复一段 Lua |
| 一个 Lua 管四把 key（全局 + 个人） | 更严格，但要重写已上线且被测试钉住的全局账本；「全局成功、个人失败」的回滚语义仍要单独处理 |
| **默认值 + 表覆盖 + 独立个人账本** | 见下；回滚语义显式、失败面窄 |

## 决策

### 1. 上限的来源：环境默认值 + 表覆盖

- `ONCALL_USER_DAILY_BUDGET_CNY`（默认 0）是所有用户的默认上限，0 = 不限制；
- `user_budgets` 表按用户覆盖（`daily_cents`，迁移 0013）；**0 是显式的「该用户不限」**，
  与「没有行」不同——后者的默认值可能非零；`DELETE` 才回到默认值；
- 读取走 `UserBudgetPolicy`：整表读进内存、2 秒 TTL（与 [ADR-0014](0014-tool-policy-overrides.md)
  的工具覆盖同一种取舍），单进程写后立即失效，多副本最长 2s 生效；
- 库读不到时网关用默认值与上一份快照，不让聊天 500：预算闸门的作用是"别花超"，
  全局日预算仍独立兜底；管理页则要求读真实值（`allow_stale=False`），不能拿旧快照当现状。

### 2. 账本：按用户独立记账，复用全局账本的 Lua

`app/core/limits.py` 新增 `UserBudgetLedger`（内存 / Redis 两实现）：

- key 带 `user_id` 与 UTC 日：`oncall:budget:user:{user_id}:{day}`（预扣明细 hash 另加
  `:reservations:`），日切后自然过期；
- 预扣/结算复用全局账本的同一段 Lua（脚本不变），只是 `limit` 从 ARGV 传入：
  覆盖随时可改，上限不能钉死在构造参数里；
- Redis 不可用时退化为进程内账本并打 warning（与全局账本同一取舍：宁可只在单实例生效，
  也不能让聊天 500）；结算按凭证里的 `backend` 回到预扣时的后端，不串账；
- `BudgetReservation` 增加 `user_id`，用户账本拒绝结算没有 `user_id` 的凭证。

### 3. 闸门位置：网关，在模型调用之前

`ModelGateway.chat()` 的顺序固定为：单 run 预算检查 → 全局预扣 → 个人预扣 → 调 provider。

- 个人额度不足时，**先把全局预扣按 0 结算还回去**，再抛 `BudgetExceeded`
  （`run.failed(BUDGET_EXCEEDED)`，`payload.category=model`）——一次被拒的调用不能占着
  当天的全局额度；
- provider 失败或抛非 `ProviderError` 时，两个预扣都按 0 结算，不泄漏；
- 成功时按实际 `cost_cents` 同时结算两个账本（同一笔花费、两个视角）；
- 不配置个人预算（`user_budget` / `user_limits` 任一为 None）时行为与以前完全一致，
  最小部署与测试不受影响。

### 4. 不自动回填历史花费

个人账本从「配置生效后的第一次调用」开始累计；当天此前已经花掉的钱不计入个人额度
（`model_calls` 与 `runs` 有全量数据可查）。按历史回填要在管理接口里查库再写 Redis、
还要处理并发写，v1 不做，写进「待定」。

### 5. 只约束模型调用

工具与检索不花钱；`ONCALL_MOCK_MODE=true` 时不经过网关，成本恒为 0，个人预算不生效——
与全局预算的现有语义一致（mock 模式本来就不会触发预算闸门）。

### 6. 管理接口（`/api/admin/budgets`）

| 方法 | 路径 | 行为 |
|---|---|---|
| GET | `/admin/budgets` | 默认值 + 全部覆盖（含修改人与时间） |
| PUT | `/admin/budgets/{user_id}` | 写入/更新覆盖；回读一次返回库里的 `updated_at`；`daily_cents` 0–1,000,000（1 万元/天，防手滑） |
| DELETE | `/admin/budgets/{user_id}` | 删除覆盖、回到默认值；幂等（不存在也 204） |

要求 `ONCALL_ADMIN_ROLES`；库不可用返回 `503 DATABASE_UNAVAILABLE`；`user_id` 不允许空白。

### 7. 展示：花费仍以 `model_calls` 为真相源

成本页新增「个人日预算」卡片（默认值、覆盖表、设置/撤销）。账本只用于闸门，不用于展示：
`model_calls` 是计量明细，账本有 TTL、Redis 故障时还会退化为进程内，拿它做展示会自相矛盾。

## 后果

- 正面：成本能落到人头；改额度不重启；被拒的请求不花钱、也不占全局额度；
  未配置个人预算的部署行为零变化。
- 代价：配置了个人额度时，每次模型调用多一次 Redis 往返（预扣），结算多一次；
  全局与个人是两笔独立预扣，进程崩在两次之间会留下全局预留——与 ADR-0013 已知的
  「预扣泄漏」同类，最坏让当天预算偏保守，日切自愈。
- 语义边界：没有租户/部门维度（`Identity` 只有 `user_id` + `roles`，等接 IdP 后再说）；
  个人额度按 UTC 日累计、不跨日结转；被拦下是 `run.failed` 而不是 `429`（与全局预算一致，
  429 留给请求限流）；个人额度配得比全局日预算还大时**永远不会先触发**（网关先扣全局），
  管理页不阻止这种配置，文档里写明它等于没设。
- 管理页多一次回读（PUT 后读一次库），为的是响应里的 `updated_at` 能直接填表格。

## 待定

- **租户 / 部门维度**：`Identity` 目前只有 `user_id` + `roles`；接 IdP 拿到组织信息后，
  再决定是「部门共享池」还是「部门限额汇总」。
- **当天历史回填**：现在账本从配置生效后开始累计；要按 `model_calls` 初始化，
  需要一次带并发保护的写 Redis。
- **额度耗尽后的降级**：当前直接 `run.failed`；可以考虑切本地模型或只读模式，
  但那会把「预算」和「降级」两套策略搅在一起。
- **预扣泄漏的观测**：与 ADR-0013 同一类问题（进程崩在预扣与结算之间、Redis 结算失败
  保留预扣），目前只有 warning 日志，没有「未结算预留」报表。
- **两本账的原子性**：要严格一致得让一个 Lua 同时管全局与个人四把 key；现在多一次往返，
  换来不动已上线的全局账本。
- **按量计费的展示**：成本页只展示 `model_calls` 聚合，个人额度的「已用 / 上限」
  没有在同一张表里拼出来（已用在下方按用户分组的表里）。
