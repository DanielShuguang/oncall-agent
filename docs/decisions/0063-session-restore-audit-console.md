# ADR-0063：会话恢复审计管理页

## 背景

ADR-0059–0062 已经把「谁在何时恢复了哪些会话」落成审计表，并提供管理员只读
列表、按用户/会话过滤、keyset 分页与 CSV 导出。但这些能力只有 API：管理员要
查一次恢复记录，得自己拼 `curl`、处理游标，非技术管理员基本用不了；审计表
保留 365 天，页面缺失会让这套治理数据只停留在数据库里。

## 备选方案

| 方案 | 为什么否决 |
|---|---|
| 只写 API 文档，不做页面 | 审计的使用者是管理员/审计人员，不应要求他们会用 curl 与 base64url 游标 |
| 把审计塞进审批中心 | 数据源、权限和心智模型都不同；审批页已经承载待办、统计与导出 |
| 先加审计总数，再做页面 | 页面没有总数也能用「已加载 N 条 + 加载更多」；总数是独立口径，先不混进来 |
| 做成可编辑/可删除的审计页 | 审计是只读凭据，不允许在页面上改历史 |
| 新增独立后端聚合接口 | 列表/导出接口已经够用，再加一层只会多一套游标与权限口径 |

## 决策

1. 新增管理后台路由 `/console/audits`（ConsolePage 新 Tab「审计」），懒加载
   `AuditPage`；数据来自现有 `GET /admin/session-restores` 与
   `/export`，不新增后端接口。
2. 页面只读：展示恢复时间、用户、请求数/实际恢复数、恢复的会话 id；不提供
   edit/delete，不展示会话正文、消息或工具参数。
3. 过滤条件为 `user_id` 与 `session_id` 精确匹配；点「筛选」才应用，「清除」
   回到全部；应用/清除时立即清空旧列表并失效在途请求，再从第一页重新加载，
   避免新过滤条件下闪现旧行。
4. 分页沿用服务端 keyset：每页 20 条，底部「加载更多」；没有总数，显示
   「已加载 N 条」，避免再引入一次 COUNT。
5. 导出复用 `GET /admin/session-restores/export`，按当前已应用过滤导出；
   最多 5000 条，截断时页面明确提示；文件名固定 `session-restores.csv`；
   浏览器下载触发抽到 `web/src/lib/download.ts`，与审批导出共用。
6. 无迁移、无后端改动；权限仍由 `require_admin` 判定，非管理员请求返回 403，
   页面显示错误卡，不在前端伪造权限。

## 后果

- 管理员终于可以在浏览器里完成「按用户/会话查恢复历史 → 翻页 → 导出」，
  不必手工处理游标。
- 页面没有总数与跳页，只能顺序翻；审计量很大时仍要依赖过滤或导出。
- 非管理员进入该 Tab 会看到 API 的 403 文案；前端不做角色隐藏，避免出现
  「有权限但看不到入口」的另一套权限逻辑。
- 会话 id 以原始字符串展示，长 id 可能换行；页面不做名称映射（没有 IdP/会话
  名称目录）。
- 导出动作仍未落下载审计；CSV 也不是防篡改证据，页面只是审计表的只读视图。

## 验证

- 前端 **84 tests / 17 files**；`tsc --noEmit`、`oxlint` 0/0（72 files/231 rules）、
  `oxfmt --check`（80 files）、`pnpm build` 通过。
- 新增 `web/src/api/sessionAudits.test.ts`：列表查询串（用户/会话/cursor/limit）、
  无过滤导出不带查询串、导出读取 `X-Export-*` 头。
- 后端未改，沿用 **496 passed + 40 skipped**、Postgres **533 + 3**、
  Postgres + Redis **536 passed**、`ruff` 194 files / `mypy` 113 files。
- 浏览器手工验收未执行；页面行为由类型检查、构建、API 客户端单测与后端契约测试保障，
  上线前建议按 `/console/audits` 的过滤、翻页、导出、403 四条路径点一遍。

## 待定

- 审计总数与跳页（当前只显示已加载条数）；
- 页面内按 `session_id` 反查的快捷入口/详情抽屉；
- 下载审计（谁在何时导出了哪些过滤条件）；
- 管理员跨用户恢复/清理（ADR-0049 待定，权限与隐私设计更大）。
