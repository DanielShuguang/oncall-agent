# ADR-0005 · 流式协议选 SSE 而非 WebSocket

- 状态：已采纳
- 日期：2026-11-08

## 背景

Agent 执行过程中需要把 6 类事件（message/step/tool_call/tool_result/approval/error）实时推给前端，同时要支持断线续传。

## 方案对比

| 维度 | SSE | WebSocket |
|---|---|---|
| 方向 | 单向（server→client） | 双向 |
| 上行 | 普通 HTTP POST 足够 | 同一条连接 |
| 企业内网代理 | 走 HTTP/1.1，几乎都放行 | 常被网关/代理拦截或超时断开 |
| 断线续传 | 原生 `Last-Event-ID` | 需自己实现序号与补发 |
| Nginx 配置 | `proxy_buffering off` | 需 `Upgrade` 头与长连接配置 |
| 我的经验 | iunit 项目做过 LSP + SSE | 用过，但没做过续传 |

## 决策

选 **SSE**，用 `fetch` + `ReadableStream` 而非 `EventSource`（需要 POST 与自定义鉴权头）。

## 理由

1. Agent 事件本质是**单向推送**，双向能力用不上
2. 私有化交付环境的内网代理对 WebSocket 不友好，这是真实踩过的坑
3. `Last-Event-ID` 与事件表天然配合：前端只要记住 `seq`，重连补拉即可
4. 与我的存量经验同构，能讲到协议层

## 后果

- 正面：部署简单、续传免费、调试直观（curl 就能看）
- 负面：HTTP/1.1 下浏览器同域并发连接数有限（6 个），多标签页会排队
- 缓解：HTTP/2 部署；或对单用户限制同时 1 个活跃流；长任务改用"提交 + 轮询/SSE 混合"

## 设计约束

- 事件必须先落库再推送（保证可回放）
- 每 15s 发 `: heartbeat` 注释行保活，不占 `seq`
- 前端按 `\n\n` 分帧，处理半帧，遇到未知 `event` 忽略而非报错
