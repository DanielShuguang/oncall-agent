# ADR-0037 · 工具配置变更历史

> 状态：已采纳（2026-11-12）
> 关联：[ADR-0014](0014-tool-policy-overrides.md)（工具覆盖与 2s 缓存）、
> [ADR-0021](0021-data-retention.md)（数据保留）、[docs/06](../06-tool-governance.md)

## 1. 背景

`tool_settings` 只保存每个工具的**当前**覆盖：`enabled`、`roles`、最后修改人
`updated_by` 与 `updated_at`。管理页可以随时改启用开关或整份权限矩阵，但改完只留下
「最后是谁改的」，没有「改之前是什么」。

ADR-0014 的待定里已经记着这个问题：

> 是否需要配置变更历史表（谁在何时把哪个工具从哪些角色改成哪些角色）

这不是一个抽象诉求。企业服务台交付时，安全/审计会问：

- 上周三谁把 `create_ticket` 的角色从 `employee` 收紧到 `admin`？
- 某次故障前 `query_cmdb` 被谁禁用过？恢复了吗？
- 权限矩阵那次整表保存，到底动了哪几个工具？

结构化日志（`tool_setting_updated` / `perm_matrix_updated`）能回答一部分，但日志有
保留期、不可按工具查询，也不能在管理页里直接看。`updated_by` 只覆盖最后一次修改。
审批有 `approvals` 表做长期证据，工具配置却没有对应物——这是治理链上的一段空白。

## 2. 备选方案

| 方案 | 结果 | 原因 |
|---|---|---|
| 只靠结构化日志 | 否决 | 日志会轮转/按保留期清理；没有「按工具查历史」的接口，排障要翻日志平台 |
| 把配置变更写成 `run_events` | 否决 | 事件必须挂在 run 上；工具配置是环境级操作，没有 run，硬塞会污染事件流与保留策略 |
| 只保留 `updated_by` 最后一人 | 否决 | 只回答「谁最后改的」，改前值、改了几个工具都丢失 |
| 每次管理页保存都记一行（含无变化） | 否决 | 重复点保存会产生噪声，审计价值被稀释 |
| 追加式 `tool_setting_changes` + 同事务写入 | **采纳** | 查询简单、可长期保留、与配置写入原子；字段只存覆盖快照，不含工具定义 |

## 3. 决策

1. **新增追加式表 `tool_setting_changes`**：`id`（BIGSERIAL）、`tool_name`、
   `changed_by`、`changed_at`、`source`（`tool` / `matrix`）、`before` / `after`
   （JSONB，`NULL` 表示没有覆盖、走代码默认）。索引 `(tool_name, changed_at DESC)`。
   工具定义仍在代码里，表里没有 `tool_settings` 外键。
2. **一次管理写入 = 每个真正变化的工具一行**。PATCH 单工具开关记一行；权限矩阵整表
   保存时对比保存前后的覆盖集合，只记录实际变化的工具（包括「恢复默认」导致的删除）。
   内容没变的保存不落行。
3. **与配置写入同事务**：InMemory 与 Postgres 存储在 `upsert` / `replace` 的同一个
   事务里写设置行与历史行。历史写失败则整次配置写入回滚，不会出现「配置改了但审计
   没记」。
4. **`before` / `after` 存完整覆盖快照**，而不是只存 diff：`{"enabled": bool|null,
   "roles": list|null}`。`null` 表示没有覆盖；`enabled=null` 表示继承，`roles=null`
   表示继承、`[]` 表示所有登录用户。这样能还原「从禁用改回继承」这类动作。
5. **只记录管理 API 的写入**（`source=tool|matrix`）。进程内直接调
   `policy.set_override(..., updated_by=...)` 的系统/测试写入没有可信的「谁」，不写
   历史；需要审计的写入必须走管理接口。
6. **新增 admin-only `GET /admin/tools/{name}/history?limit=20`**：按时间倒序，默认
   20、最多 100；按名字查询，**不要求工具仍在注册表**（下线/改名后历史仍可查，未知
   名字返回空列表）；库不可用返回 503，不把故障显示成「没有历史」。
7. **v1 不设保留期、不做编辑/删除**：与审批决议行一样属于长期审计证据；增长量与
   管理员操作次数同阶，远小于 run 事件。需要冷归档时并入 ADR-0021 的清理体系另议。
8. **管理页加「历史」入口**：展示时间、操作人、来源、`before → after`；不提供回滚
   按钮（回滚应走一次新的显式保存，留下新的审计行）。

## 4. 后果

- 安全/审计可以按工具回答「谁在何时把启用/角色从什么改成什么」，不依赖日志保留期；
  工具下线/改名后历史仍按旧名字保留。
- 权限矩阵保存的审计粒度是「每个变化的工具一行」，不是「一次矩阵提交一行」；同一
  次提交的行 `changed_at` 相同（Postgres 同一事务的 `now()`；内存实现取同一批次
  时间）、按工具名排序写入。
- 管理写入仍是 last-write-wins：`before` 在写事务外读取，两个管理员并发修改同一工具
  时，后一个请求的 `before` 可能不是前一个请求的 `after`，审计序列不保证首尾相接；
  每行的 `after` 是当次请求实际写入的值。需要严格因果链时应加乐观锁/行锁，v1 不做。
- 矩阵保存会把已下线工具的残留覆盖一并清掉，并各记一条删除记录；这是清理，不是新
  变更。管理页只列已注册工具，因此下线工具的历史只能通过 API 按旧名字查。
- 表只增不减，长期会累积；当前判断是管理操作频率低，暂不清理。将来接对象存储冷归档
  时，历史表需要与审批决议行一起设计。
- 直接改数据库（绕过 API）不会留下 `changed_by` 可信的记录；这与其他治理表一致，
  DBA 变更不在应用审计范围内。
- `tool_settings.updated_by` 仍保留（最后修改人，管理页展示用），但它不再是历史来源。

## 6. 待定

- 历史保留期与冷归档（与 ADR-0021 / ADR-0027 的决议行一起设计）。
- 管理员身份目录：`changed_by` 目前是 JWT `sub`，没有姓名/部门可展示。
- 导出（CSV/JSON）与按时间范围筛选；v1 只按工具查最近 N 条。
- 矩阵提交的「一次操作」聚合视图（现在按工具行展示，没有 batch id）。
- 回滚按钮：需要明确「回滚也是一次新变更」的交互与权限。
