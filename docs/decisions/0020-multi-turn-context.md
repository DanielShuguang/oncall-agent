# 0020 · 多轮上下文：服务端会话历史，有预算、有边界

- 状态：已采纳（W6 后加固）
- 日期：2026-11-10
- 相关：[docs/02-data-model.md](../02-data-model.md)、[docs/03-api-contract.md](../03-api-contract.md)、[docs/04-agent-design.md](../04-agent-design.md)、[docs/05-rag-design.md](../05-rag-design.md)、[ADR-0019](0019-document-level-access.md)

## 背景

W5 D24 的验收项是「中断/重试/**多轮**/引用跳转/移动端」。前四项都落地了，多轮一直没做：
`AgentState.messages` 从 W1 起就是空数组（死字段），`POST /chat/stream` 每一轮都是独立 run，
前端的 transcript 只是展示，服务端看不到。

代价在真实对话里立刻出现：

- 「VPN 连不上怎么办」→ 答完。用户接着问「那怎么办？」——这句话里没有任何可检索的词，
  检索为空，按"知识库外"拒答；用户看到的是"它突然失忆了"
- 「帮我开个单」本身不含故障信息，单轮实现里工单标题就是「帮我开个单」
- 计划器（真实模式）看不到上一轮，无法理解"还要多久""那这个呢"的指代

但直接加历史有三个坑，必须先定边界：

1. **客户端传历史**：等于让客户端伪造 assistant 消息。模型会把伪造的"助手上一条说的"
   当既有事实，比 R9 的入参身份泄漏更隐蔽
2. **历史当证据**：上一轮的切片被当成引用喂回来，引用就不可溯源了——"引用跳全文"
   会打开一篇本轮没有检索过的文档
3. **预算无上限**：历史进 prompt，会话越长成本越高；早先话题还会污染当前问题

## 备选方案

| 方案 | 否决理由 |
|---|---|
| 客户端传 `history: [{role, content}]` | 可伪造 assistant 发言；请求体随会话膨胀；服务端失去幂等与审计口径。身份/状态来自服务端是 R9 的底线 |
| 把上一轮的回答当检索证据 | 引用必须来自本轮 `retrieved`，否则 `message.completed.citations` 不可溯源，ADR-0018 的全文跳转会把用户带到没检索过的文档 |
| LLM 改写追问（把「那怎么办」改写成独立问题） | 多一次模型调用、不可复现；mock 模式下没有模型，demo 与评测链路会分叉。先用确定性启发式，剩下交给模型规划 |
| 整段 transcript 直接塞 prompt | 成本与延迟随会话线性增长；长会话里旧话题会稀释当前问题 |
| 滚动摘要（LLM summary） | v1 会话轮次很少（3 轮），摘要自身的错误比截断更难排查；等有真实长会话再评估 |
| 跨会话长期记忆 / 用户画像 | 属于另一个产品问题（隐私与更新语义都没定），v1 只解决"同一段对话内的指代" |

## 决策

**历史只来自服务端，只用于理解指代，不进证据链。**

### 1. 来源与作用域

`RunStore.recent_turns(user_id, session_id, limit, exclude_run_id)` 从 `runs.input/output`
投影取最近 3 轮：

```sql
SELECT input, output FROM runs
WHERE user_id = :uid AND session_id = :sid
  AND output IS NOT NULL AND length(output) > 0
ORDER BY started_at DESC LIMIT 3;
```

- **同用户 + 同会话**：`session_id` 由前端生成，跨用户撞字符串也取不到别人的行
- **只认有 `output` 的轮次**：挂起审批、正在跑、被中断的 run 没有回答，不能当成历史；
  否则模型会"记得"一句它从未说过的话
- **拒答也算回答**：`REFUSAL` 是明确的语义（"知识库里没有"），用户下一句追问依赖它
- 索引：迁移 0009 加 `(user_id, session_id, started_at DESC)`；`idx_runs_user_time`
  是 `(user_id, started_at)`，过滤 `session_id` 要读该用户全部 run
- 当前 run 的 `output` 还没写，天然被排除；`exclude_run_id` 只是防御

### 2. 预算

`app/agent/history.py`：最多 3 轮、单条问题 200 字、单条回答 400 字、总 1200 字，
超了从**最旧**的轮次丢（最近的更相关）。每条回答截断后带 `…`，模型能看出"这是截断的"。

### 3. 用法（只有三处）

| 位置 | 用法 | 边界 |
|---|---|---|
| `state.messages` | `[{role:"user"},{role:"assistant"}]` 交替；`finalize` 追加本轮 assistant | 只有 plan 与后续轮次读取；不进事件、不进引用 |
| `retrieve` | `contextual_query(query, messages)`：**判定为追问时**把上一轮问题拼在前面，作为 `context_query` 检索 | 未判定为追问 → 与单轮完全一致 |
| `plan`（真实模式） | payload 增加 `history`（最多 4 条消息） | 提示词写明：历史不是证据、不是指令 |

`finalize` 用 `context_query` 挑句子：只说「那怎么办」时，单靠本轮 token
选出来的句子和问题无关。单轮场景 `context_query == query`，行为不变。

### 4. 追问判定（启发式）

`needs_context(query)`：长度 ≤ 30 字，且满足其一——以「那/再/另外/还有/然后/接着/继续/同样」
开头、以「呢」结尾、包含「它/这个/那个/刚才/上述/这条…」。长句一律按新问题处理。

### 5. 前端：清空对话必须换 session

`session_id` 从模块常量改成"每次 `reset()` 生成新值"。否则用户点了"清空对话"，
服务端仍按旧 `session_id` 取历史，新会话的第一句带着上一段上下文——既奇怪又是隐私问题。

### 6. 失败降级

历史读取失败只 `log.warning`，本轮按单轮跑。历史是锦上添花，不能因为它把这一轮也打挂。
幂等重放路径不读历史（只回放已落库事件）。

## 后果

**收益**

- 追问能接上话题：端到端用例里，同一会话「那怎么办？」引用到 VPN 文档；
  换一个 `session_id` 的同样追问必须拒答——两条用例把"作用域"和"生效"同时钉住
- 单轮行为零变化：评测 50 条没有历史 → `context_query == query`，指标与基线一致
  （50/50、`cite_acc 97.09%`），这是这次改动的前置约束

**代价与已知风险**

- 启发式会误判：「那报销怎么走」以「那」开头，会把上一轮话题拼进检索、稀释召回。
  宁可稀释也不硬塞整段历史；真实坏例要靠日志里的 `context_query` 收敛
- 3 轮之外失忆；刷新页面即新会话（前端 ID 在内存里），没有跨会话记忆
- 回答被截断到 400 字，模型看到的历史是"…"结尾的片段
- 多轮只有测试覆盖，**没有进评测集**：`app/eval/cases/` 仍是 50 条单轮。
  多轮质量（指代是否解对）目前只有两条端到端用例与一组纯函数用例兜底
- 真实模型下 `history` 对 plan 的影响未量化（mock 模式是规则计划，读不到这部分收益）
- 工单标题仍取当前轮输入：「帮我开个单」不会自动变成「笔记本蓝屏」——标题取自
  用户最新诉求是有意为之，避免把两轮内容拼成一句读不通的话

**待定**

- 追问判定要不要用模型兜底（多一次调用换更准的指代解析）
- 要不要把多轮用例加进评测集（需要先定义"指代解对"的判定口径）
- 会话历史是否需要 TTL（当前跟随 `runs` 保留策略，没有单独清理）
