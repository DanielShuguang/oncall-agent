# ADR-0055：批量恢复逐条结果

## 背景

ADR-0049 的批量恢复只返回 `{"restored": n, "requested": m}`。用户一次勾选十几个
已移除会话时，如果只恢复了其中一部分（例如另一个标签页已经恢复过、列表里混进了
已经失效的 id），界面只能告诉他「恢复了 8 个」，无法指出剩下的 4 个是谁；重新
拉取列表后，失败项已经被过滤掉，用户只能自己对照。

恢复本身只是删 `hidden_sessions` 的一行，逐条结果不会改变数据一致性，也不会
引入新的写入路径；缺的只是把存储层已经知道的「哪些 id 真的删掉了」带到响应和
前端提示里。

## 备选方案

| 方案 | 否决原因 |
|---|---|
| 保持计数 + 前端对比恢复前后的列表 | 列表可能分页/筛选，恢复后重新拉取才能对齐；前端对比既不知道服务端删了哪些行，也会被并发恢复干扰 |
| 只返回失败的 id 列表 | 信息等价但语义绕：调用方要先减去失败项才知道成功项；顺序也不如逐条结果直观 |
| 返回 `restored` / `missing` / `forbidden` 三类 | `forbidden` 会泄露「这个 session_id 存在但属于别人」，与 ADR-0049 不泄露存在性的决定冲突；`missing` 与 `forbidden` 无法在不泄露的前提下区分 |
| 不加响应字段，另做恢复审计接口 | 审计解决「谁在何时恢复了哪些」，不解决本次请求里哪些 id 生效；先做前者成本低、收益直接 |

## 决策

1. **响应增加 `items`，保留计数**。`POST /sessions/hidden/restore` 返回
   `{"restored": n, "requested": m, "items": [{"session_id": "...", "restored": true|false}]}`；
   `items` 与去重后的请求顺序一致，`restored` 仍是真正恢复的数量，`requested`
   仍是去重后的数量。旧客户端只读前两个字段不受影响。
2. **逐条只区分「恢复了 / 没恢复」**。`restored: false` 刻意合并「不存在」「属于
   别人」「本来就没移除」三种情况，不返回 `forbidden` 或更细的原因；这与单条恢复
   统一 404 的口径一致，避免把别人的会话是否存在变成可探测的旁路。
3. **存储层返回恢复的 id 集合**。`RunStore.unhide_sessions` 从返回 `int` 改为返回
   `set[str]`：内存实现收集真正 `pop` 成功的 id，Postgres 用
   `DELETE ... RETURNING session_id` 收集；API 负责按请求顺序映射成 `items`。
   不新增迁移、不新增索引、不写审计。
4. **前端展示部分成功提示**。批量恢复成功后按 `items` 统计失败数，在已移除折叠区
   显示中性提示：「已恢复 8 个；4 个未恢复（可能已被恢复或不在本人已移除列表）」；
   全部未恢复时改为「没有会话被恢复；N 个未恢复……」，不显示「已恢复 0 个」。
   仍然重新拉取已移除列表与普通列表，以服务端结果为准，不用逐条结果去改本地列表；
   提示不占用错误样式，开始新的搜索/恢复、展开或收起折叠区时清空。滚动升级期间
   旧后端响应没有 `items`，前端退回只读 `restored` 计数，不把成功的恢复报成失败。
5. **幂等语义不变**。同一批再调用时 `restored` 为 0，所有 `items[].restored` 为
   false；空列表/超过 50 个/空白 id 仍然 422。
6. **范围**：不做恢复审计、不做管理员跨用户恢复、不做「恢复并打开」。审计需要
   新表、保留期和读取入口，留作独立 ADR。

## 后果

- 响应最多多 50 个小对象，客户端可以准确告诉用户哪些 id 没生效；不需要额外请求。
- `restored: false` 不区分原因，用户仍需知道「可能已被恢复或不在本人已移除列表」；
  这是隐私与可解释性之间的刻意取舍。
- 存储层契约从计数变成集合，调用方只有 API 一处；测试需同步从 `== 1` 改为集合比较。
- 没有审计：谁在何时恢复了哪些会话仍然查不到；这是 ADR-0049 已记录的边界，本 ADR
  不扩大范围。

## 验证

- 默认 `pytest`：**485 passed + 40 skipped**；真实 Postgres：**522 passed + 3
  skipped**；Postgres + Redis：**525 passed**。
- 契约用例覆盖：去重后请求顺序、`items` 布尔值、重复恢复全部 false、空列表/51 个/
  空白 id 422；内存与 Postgres 的 `unhide_sessions` 都返回恢复 id 集合。
- 前端单测覆盖提示文案的全成功、部分成功、全部未恢复与旧响应无 `items` 四种情况。
- `ruff check` / `ruff format --check`（188 files）/ `mypy app`（110 files）通过；
  前端 `tsc`、**79 tests / 16 files**、`oxlint` 0/0、`oxfmt --check` 76 files、
  `pnpm build` 通过。无迁移。
